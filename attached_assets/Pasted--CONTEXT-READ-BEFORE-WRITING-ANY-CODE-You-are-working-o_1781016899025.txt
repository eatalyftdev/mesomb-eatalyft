# TASK 2 — IMPLEMENT FULL WEBHOOK SIGNATURE VERIFICATION

Implement a `verifyMeSombWebhook` utility at `src/lib/mesomb-webhook.ts` with this exact logic (from the official MeSomb docs):

```typescript
import crypto from 'crypto';

export interface VerifyWebhookOptions {
  rawBody: string;
  signatureHeader: string;
  webhookSecret: string;
  toleranceSeconds?: number; // default 300 (5 minutes)
}

export function verifyMeSombWebhook(opts: VerifyWebhookOptions): void {
  // 1. Check header present
  // 2. Split "t=<ts>,v1=<sig>" format
  // 3. Validate timestamp is a finite number
  // 4. Check timestamp age against toleranceSeconds — reject if too old (replay attack protection)
  // 5. Build signed payload as: `${timestamp}.${rawBody}`
  // 6. Compute HMAC-SHA256(webhookSecret, signedPayload).digest('hex')
  // 7. Use crypto.timingSafeEqual for comparison — NEVER use === string comparison
  // 8. Throw descriptive errors on any failure so the caller can return 400
}
```

# TASK 3 — REBUILD THE WEBHOOK HANDLER

Rewrite the webhook handler at `src/routes/webhook.ts` (or wherever it currently lives). The handler must follow the **recommended processing model from the MeSomb docs**:

1. **Read raw body** (do NOT use `express.json()` middleware before this route — use `express.raw({ type: 'application/json' })` so the raw buffer is available for signature verification)
2. **Read `X-MeSomb-Webhook-Signature` header**
3. **Call `verifyMeSombWebhook`** — if it throws, return `400` immediately
4. **Parse JSON** from the raw body
5. **Check `X-MeSomb-Webhook-Event-Id` header OR `event.id` for deduplication** — query Supabase `webhook_events` table; if already processed, return `200` without re-processing
6. **Enqueue or synchronously route** the event to the correct handler by `event_type`
7. **Return `200 OK`** or `204 No Content` immediately — do NOT block on heavy processing
8. **Process the event** (either inline for now, or via a Supabase queue table for async later)

Route all event types to dedicated handlers:

```typescript
// Event routing map
const handlers: Record<MeSombEventType, (event: MeSombWebhookEvent) => Promise<void>> = {
  'payment.transaction.success': handlePaymentSuccess,
  'payment.transaction.failed': handlePaymentFailed,

  'checkout.session.expired': handleCheckoutExpired,
  'checkout.session.canceled': handleCheckoutCanceled,

  // ... etc
};
```

# TASK 4 — IMPLEMENT ALL TRANSACTION STATUS HANDLERS

Implement each handler. Each one must:

### `handlePaymentSuccess(event)`
- Extract `data.object` as `MeSombTransactionObject`
- Upsert into Supabase `payments` table with `status: 'SUCCESS'`, `mesomb_pk`, `fin_trx_id`, `amount`, `fees`, `service`, `reference` (your internal trxID), `customer`, `ts`
- Use `reference` field to locate the internal order/trip/booking in Supabase and update its `payment_status` to `'paid'`
- For ride orders: update `rides` table; for food: update `orders` table; for parcel: update `parcel_orders` table; for bus bookings: update `bus_bookings`; for hotel: update `hotel_bookings` — use the `reference` prefix pattern (e.g. `RIDE-`, `FOOD-`, `PARCEL-`, `BUS-`, `HOTEL-`) to determine which table to update
- Store `fin_trx_id` (operator transaction ID) for reconciliation

### `handlePaymentFailed(event)`
- Upsert into Supabase `payments` table with `status: 'FAILED'`
- Update the linked order's `payment_status` to `'failed'`
- Log the `message` field from the transaction for debugging
- Do NOT throw — a failed payment is a valid business event, not an error

### `handleCheckoutCompleted(event)`
- Extract `data.object` as `MeSombCheckoutSessionObject`
- Update checkout session record in Supabase
- If `payment_status` on the session object is `paid`, trigger the same fulfillment logic as `handlePaymentSuccess`

### `handleCheckoutExpired(event)` and `handleCheckoutCanceled(event)`
- Mark checkout session as expired/canceled in Supabase
- Release any reserved inventory or booking holds

### `handleSecurePayFunded(event)`
- Mark the linked order as `'funded'` — seller notified to prepare

### `handleSecurePayReleased(event)`
- Mark as `'completed'` — funds released to seller

### `handleSecurePayRefunded(event)`
- Mark as `'refunded'` — buyer returned funds

# IMPORTANT RULES

- Never use `===` to compare HMAC signatures — always use `crypto.timingSafeEqual`
- Always use the **raw request body** (not re-serialized JSON) for signature verification
- Always return `200` or `204` for events that are received but unrecognized — never `404` or `500` for unknown event types (that would trigger unnecessary MeSomb retries)
- Failed transactions (`payment.transaction.failed`) are **normal business events** — handle them gracefully, do not treat as system errors
- The `reference` field in the transaction payload is the `trxID` you passed during `makeCollect` — always pass your internal order/booking ID as `trxID` so you can look it up on webhook receipt
- `isOperationSuccess()` and `isTransactionSuccess()` can differ — always check both and log accordingly
